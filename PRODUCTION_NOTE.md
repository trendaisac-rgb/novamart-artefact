# Production note: NovaMart internal assistant

**Platform.** I would keep the Claude API for production. The prototype depends on three things that are native there: reliable tool calling, prompt caching for the fixed prefix (rules, catalog, tool schemas, which is most of every request), and a model tier per job (Sonnet for the agent, Haiku for grading and clustering, Opus only if evals show Sonnet failing on a class of questions). The provider boundary is a single file, so this is not a lock-in decision. If NovaMart is already standardized on Google Cloud or Azure with data-residency commitments, I would re-evaluate Gemini or OpenAI through that cloud and keep the same architecture; the retrieval, tools, evals and gap loop do not change.

**Managed offering vs. custom build.** A hybrid. I would use the platform's managed agent runtime (Claude Managed Agents, or the equivalent) for hosting, session state and the operational basics, because NovaMart has not committed to a platform yet and should not start by running agent infrastructure. I would keep three things custom and small, because they carry NovaMart's business logic and change weekly: the retrieval layer over NovaMart's documents, the tools that talk to NovaMart's systems (orders, tickets, POS), and the eval suite. A fully managed enterprise chat product gets a pilot running in days but makes the "cite or decline" rule, the structured `respond` contract and custom evals harder to enforce; a fully custom build spends the first month on plumbing. The split above is the one I have seen hold up in delivery.

**Connecting real data.** Three sources, three patterns. (1) Policies: today they live in a mix of PDFs, SharePoint pages and emails. I would convert them into one markdown file per policy with a heading per rule, owned by Operations, in a Git repository. A merge to main re-indexes. This is the single highest-leverage step: most "the assistant was wrong" cases on previous projects were "the document was wrong or stale". (2) Orders: a read-only API client with the same `get_order_status` contract as the mock, authenticated per employee so audit logs show who looked up what. (3) Tickets: the escalation tool writes to the helpdesk tool NovaMart already uses. Retrieval moves to hybrid (BM25 plus embeddings) with metadata filters for region, store format and effective date, behind the same `search()` interface; the prototype's catalog-in-prompt stays for the decline behavior.

**Security and governance.** SSO for employees, store id and role on every request. Tools are allow-listed and read-only except ticket creation; the model never gets database credentials, it gets functions. No customer PII in prompts beyond what the order tool returns for the order the employee asked about, and a zero data retention agreement with the model provider, which the main platforms offer for enterprise API use. Every answer stored with its trace: question, searches, sections read, tool calls, final status and sources, so any answer can be audited back to a document version. Documents carry an owner and a review date; a policy past its review date is flagged in the catalog. Anything involving money above a limit, fraud or exceptions stays human-gated: the assistant explains the rule and opens the ticket, it does not approve.

**Evaluating and monitoring quality.** The eval suite from the prototype becomes a release gate in CI: no prompt, retrieval or document change ships below the threshold, and every fixed failure becomes a case so it cannot regress silently. In production, four signals: decline rate per topic (rising means a documentation gap, falling after a new doc confirms it closed), thumbs up/down from employees, a weekly sample of answers graded for faithfulness by the judge and spot-checked by Operations, and latency plus cost per answer. The knowledge gap report goes to the ops lead weekly with the themes to document. I would run the first four weeks in two pilot stores with Operations reading every escalation, then widen.

**Rollout.** Week 1 and 2: documents converted and owned, pilot stores, read-only. Week 3 and 4: order tool live, escalation tool live, eval gate in CI. Month 2: all stores, gap loop running weekly. The assistant is useful on day one because it is allowed to say "not covered" and someone is listening when it does.
